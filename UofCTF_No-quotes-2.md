# No Quotes 2 — writeup (uoftctf)

## Факты из исходников

### WAF
Поля `username` и `password` блокируются, если содержат **`'` или `"`**.

### SQL-запрос
Запрос собирается строковой подстановкой:

```sql
SELECT username, password FROM users
WHERE username = ('{username}') AND password = ('{password}')
```

После выполнения делается **double check**:

- `username == row[0]`
- `password == row[1]`

### `/home`
HTML читается как строка, в неё подставляется `session["user"]` через `%s`, затем строка рендерится `render_template_string(...)`.  
Это даёт SSTI, если в `session["user"]` лежит Jinja2-выражение.

---

## План атаки

1) Сделать SQLi, обойдя запрет кавычек.  
2) Пройти double check (вернуть из SQL ровно то, что ввели).  
3) Положить в `session["user"]` SSTI и на `/home` выполнить `/readflag`.

---

## 1) SQLi без кавычек через `\` в конце username

В MySQL/MariaDB `\` внутри `'...'` экранирует следующий символ.  
Если `username` заканчивается на `\`, то закрывающая кавычка после username становится `\'` и **не закрывает** строку. Следующая кавычка (та, что стоит перед паролем) становится **закрывающей для username**, а `password` начинает парситься как SQL-код.

---

## 2) Double check: “quine” для password

Нужно, чтобы `row[1]` совпал **байт-в-байт** с отправленным `password` (хотя это SQL-инъекция).  
Используется quine-конструкция:

- кладём payload в переменную `@a` как hex-литерал `0x...` (кавычки не нужны)
- восстанавливаем исходную строку через `REPLACE(@a:=0x..., 0x24, HEX(@a))`, где `0x24` — `$`

---

## 3) SSTI на `/home`

В `username` кладём Jinja2-выражение:

```jinja2
{{cycler.__init__.__globals__.os.popen(request.args.c).read()}}
```

Команду передаём параметром `c`, без кавычек: `/home?c=/readflag`.
